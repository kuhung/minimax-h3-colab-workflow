## 🔍 深度复盘：为什么之前能跑 300 秒，刚刚跑却超时了？

### 1. 之前跑通的 306 秒到底跑了什么？（v1.0 版本真相）
在项目初期通过完整运行并保留输出的存证文件 [`v1.0_minimax_h3_l4_benchmark_webp.ipynb`](./v1.0_minimax_h3_l4_benchmark_webp.ipynb) 中：
- **只渲染了无声视频，直接打包为 WebP 动画**。它根本没有加载 32kHz Audio VAE 模型，也没有经历音频潜空间解码与 ffmpeg MP4 重编码。
- **分辨率严格为 960x544**（约 52.2 万像素）。
- 在 8 步 Turbo 下，每个镜头纯视频去噪耗时稳定在 **306 秒（约 5.1 分钟）**。

### 2. 刚刚在 Colab 上跑为什么超时暴涨到 631 秒？（v1.5 版本根因）
用户在 Colab 上实测看到的日志：
```text
[03:29:37] ⏳ 渲染去噪中... 已耗时 463s
[03:32:26] ⏳ 渲染去噪中... 已耗时 631s ... (超时)
```
这是因为当时运行的正是 `v1.5` 旧架构：
1. **分辨率暴增 97.6%**：任务配置从 960x544 变成了 1344x768（103.2 万像素）。DiT 模型的计算量随空间补丁数量成非线性增加，耗时直接翻倍。
2. **CFG=3.0 的双前向算力浪费**：旧版使用了正负提示词双路编码，每一步去噪都要跑 Unconditional 和 Conditional 两次前向传播。8 步实际跑了 16 步 DiT。
3. **叠加音频解码与压制开销**：增加了 `VAEDecodeAudio`（`minimax_h3_audio_vae_fp32.safetensors`）以及 `CreateVideo`。
4. **算子慢路径回退**：Colab 默认环境为 CUDA 12.x，硬跑专为 CUDA 13.0 设计的 `int8_convrot` 会触发降级回退。
四重因素叠加，单镜头耗时直接翻倍到 630 秒以上，超过了默认心跳或超时阈值。

### 3. v2.0 实测存证数据：如何实现 165 秒极速生产与音画同出？

在最新运行并完整保留 Colab 输出的实测存证文件 [`v2_0_minimax_h3_l4_production_mp4.ipynb`](./v2_0_minimax_h3_l4_production_mp4.ipynb) 中，核心性能指标如下：

1. **单镜头耗时表现（960x544, 124 帧 @ 24fps ≈ 5.17 秒）**：
   - **分镜 1（冷启动与权重搬运）**：`243.5 秒`（文件大小 2.42 MB，含首次加载 DiT 与音频 VAE 到显存的开销）。
   - **分镜 2（热跑稳态渲染）**：`165.3 秒`（2 分 45 秒，文件大小 0.63 MB，原生 32kHz 音画合成）。
   - **分镜 3（热跑稳态渲染）**：`165.5 秒`（2 分 45 秒，文件大小 1.23 MB，原生 32kHz 音画合成）。
   - **3 镜总渲染耗时**：**574.6 秒（仅 9.58 分钟）**！
   - **稳态平均耗时**：**165.4 秒 / 镜头**，相比 v1.0 的 306 秒不仅速度提升了 **46%**，而且额外获得了高品质的双声道立体声环境音！
2. **算力单元消耗与生产成本**：
   - L4 显卡在 Google Colab 的实际费率为 **1.90 CU/小时**。
   - 3 个镜头生产总共耗费：**0.303 CU**。
   - 稳态单镜生成成本：$$1.90 \times \frac{165.4}{3600} \approx \mathbf{0.087\ \text{CU / 镜头}}$$。
   - **1 个计算单元（CU）即可稳定输出 ~11.5 个带完整音频的高清短视频分镜！**
   - Google AI Pro（每月 100~300 CU）：每月可稳定产出 **1,150 ~ 3,450 镜头**。
   - Google AI Ultra（每月 500~1,500 CU）：每月可稳定产出 **5,750 ~ 17,250 镜头**。
3. **环境与权重加载突破**：
   - **CUDA 13.0 原生激活**：实测当前 Google Colab 分配的 L4 实例已提供 PyTorch CUDA 13.0 (`cu130`) 运行库，自动点亮 `int8_convrot` 原生硬件量化内核！
   - **HF 直连 NVMe 极速就绪**：首选直接拉取 HuggingFace 官方源至本地高速 NVMe，5 大核心权重（近 40GB）**仅耗时 136.32 秒（2.27 分钟）** 即可秒级就绪并通过 safetensors 头部双校验，彻底终结了从 Google Drive FUSE 软链接读取造成的显存饥饿等待！

## 🛠️ 文件管理规约与防混淆指南

为防止后续再次出现“盲目覆盖、线上跑的与本地想的不一致”：

1. **严格单一语义版本控制，杜绝无版本号混乱**：
   - 本目录仅保留具备明确语义版本的 `.ipynb` 文件（`v1.0_*`, `v1.5_*`, `v2.0_*`）。
   - 彻底删除早期无编号文件（`minimax_h3_l4_benchmark_run_results.ipynb`、`minimax_h3_l4_production.ipynb`、`test_shanghai_mp4_audio.ipynb` 等），消除命名歧义与覆盖混乱。
   - 在 Colab 中调试与运行任务，必须指认带明确版本前缀的文件（例如生产运行选 `v2.0_minimax_h3_l4_production_mp4.ipynb`）。
2. **禁止手动在 Notebook 内部随意硬编码改动**：
   - 生产 Notebook 均由 `scripts/generate_notebook.py` 和 `scripts/build_shanghai_notebook.py` 程序化生成。
   - 生成脚本会执行 `ast.parse` 静态分析与 node 拓扑校验，确保无未定义变量、无断链节点。
3. **线上 Colab 与本地严格对齐**：
   - 每次修改后，在 Colab 中请重新上传对应的版本文件，或检查第一行 Markdown 中的 `版本标识` 是否与本地一致。
